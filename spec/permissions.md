# 권한 — 상속과 유효 권한 판정

이 문서는 "이 사람이 이 파일에 무엇을 할 수 있는가"를 정하는 규칙 하나와, 그 규칙에서
따라 나오는 케이스들을 적는다. 구현은 `backend/app/services/permissions.py` 이고, 단일 관문은
`ensure_file_access`(`services/files.py`) 다.

## 규칙 하나

> **유효 권한 = 조상 경로와 자신에 부여된 행 중 최고 수준.** (manage > write > read)

거리는 수준 결정에 관여하지 않는다. 동수준일 때 출처 표기에만 쓴다. 여기서 곧바로 나오는
성질이 이 문서의 나머지 전부다.

> **상속은 넓히기만 한다. 하위에서 좁힐 수 없다.**

`@전사 read` 를 상속받은 항목을 '특정 그룹만'으로 되돌리는 방법은 없다. 반대로 특정 그룹만
열린 항목에 `@전사 read` 를 더해 전사 공개로 넓히는 것은 그냥 된다. 승격도 마찬가지다.

좁히는 **유일한** 방법은 상위에서 `inherit_to_children=FALSE` 로 상속을 끊고 필요한 하위에
개별 부여하는 것이다.

### 왜 누적인가 (2026-07-28 변경)

종전 규칙은 '가장 가까운 조상이 이긴다' 였고, 하위에서 권한을 낮추기 위한 재정의였다. 그런데
권한 행은 **사용자가 속한 모든 그룹**에 대해 수집되므로 재정의가 같은 그룹 안이 아니라
**그룹을 가로질러** 작동했다 — 그룹B 에 read 를 준 사람이 그룹A 관리자의 manage 를 의도 없이
깎았다. 누적에서는 아무도 부여한 적 없는 권한이 생기지 않는다. 최고 수준이라도 누군가
명시적으로 부여한 것이다.

## 축이 둘이고, 비대칭 방향이 서로 반대다

| 축 | 저장소 | 상속 규칙 |
|---|---|---|
| **그룹 권한** | `file_group_permissions` | **넓히기 전용** — 조상+자신의 최고 수준 |
| **위키 스위치** | `files.wiki_enabled` (3상태) | **끄기 전용** — 명시값이 상속을 이긴다 |

방향이 반대인데도 모순이 아닌 이유는, 위키 토글이 **폴더에 상속 부여를 하지 않고 대상 파일마다
직접** `@전사 read` 를 걸기 때문이다(`grant_permission_bulk` 는 `inherit_to_children=False`
하드코딩). 상속으로 오지 않으니 파일에서 지울 수 있다. 근거는 spec/wiki-index.md
「공개는 폴더가 아니라 대상 파일에 건다」.

## 케이스

### 넓히는 방향 — 된다

| 상위 | 하위에서 하는 일 | 결과 |
|---|---|---|
| 그룹A read (상속) | `@전사 read` 추가 | 전사 공개 |
| 그룹A read (상속) | 그룹A write 부여 | write 로 승격 |
| 그룹A read (상속) | 그룹B manage 부여 | B 멤버는 manage, A 멤버는 read |
| 없음 | 위키 켜기 | 그 파일에 `@전사 read` 직접 부여 |
| 폴더 소유가 나 | — | 하위 전체 manage. **하한선**이라 그룹 부여로 깎이지 않는다 |

### 좁히는 방향 — 안 된다

| 상위 | 시도 | 실제 |
|---|---|---|
| `@전사 read` (상속) | 하위를 '특정 그룹만'으로 | 상속이 살아 전사 공개 유지 |
| `@전사 read` (상속) | 하위에서 `@전사` 회수 | 404 — 직접 부여가 없어 지울 대상 자체가 없다 |
| 그룹A manage (상속) | 하위에 그룹A read 부여 | **409 거부** — 아래 참조 |
| `@전사 read` 무기한 (상속) | 하위에 짧은 만료 부여 | 만료도 못 줄인다 |
| 폴더 소유가 나 | 하위에 낮은 그룹 권한 | 조상 소유 manage 가 이긴다 |

#### 상속보다 낮추기는 거부한다

상속보다 낮은 수준을 직접 부여하는 요청은 **409 로 거부한다**(`narrowing_conflict`).
`grant_permission`·`update_permission` 두 경로 모두에 건다.

허용하면 API 는 200 을 주고 행도 실제로 저장되지만 유효 권한은 상속된 높은 쪽 그대로다.
목록에는 그 낮은 값이 보이므로 관리자는 좁혔다고 믿는다 — **실패보다 나쁜 조용한 무효**다.
성공했는데 아무 일도 안 일어나는 것보다, 실패하고 이유를 아는 편이 낫다.

그래서 거부 사유가 **다음 행동까지 말해야 한다.** 좁히는 방법이 '상속 출처에서 하위 상속 끄기'
하나뿐이므로, 사유에 그룹명·상속 출처 폴더명·양쪽 수준·해결 경로를 모두 싣는다.

> '기획팀' 그룹은 '공유폴더'에서 관리 권한을 상속받고 있어 이 항목만 읽기(으)로 낮출 수
> 없습니다. 좁히려면 '공유폴더'에서 하위 상속을 끄고 필요한 항목에만 개별 부여하세요.

대가를 적어 둔다. '상속을 끊기 전에 하위를 먼저 낮춰 두는' 순서가 막힌다. 상속을 끊는 순간부터
하위가 잠깐 접근을 잃고, 그 뒤에 개별 부여해야 한다. 조용한 무효를 남기는 것보다 이 순서 제약이
낫다고 봤다.

`PermissionModal` 은 누르기 전에 미리 알린다 — 직접 부여 행과 부여 폼 양쪽에서 선택한 수준이
그 그룹의 상속 수준보다 낮으면 경고를 띄운다. 눌러서 실패하면 백엔드 사유가 그대로 토스트로 뜬다.

근거 데이터가 `list_permissions` 의 상속 목록이므로, 그 목록은 그룹별 **최고 수준** 한 건이다
(동수준이면 최근접). '최근접' 이었다면 조부모 manage + 부모 read 인 경우 화면이 read 를 표시해
유효 권한보다 낮게 읽히고, 경고가 **새는 방향으로** 틀린다.

**아직 남은 조용한 무효 하나** — 만료 시각은 막지 않는다. 상속 행이 무기한인데 하위에 짧은
`expires_at` 을 걸면 여전히 조용히 무의미하다. 수준과 달리 만료는 구간이 겹쳐 '더 좁다'가
단순 비교로 떨어지지 않아 보류했다.

### 상속이 애초에 안 오는 경우

| 상황 | 효과 |
|---|---|
| `inherit_to_children=FALSE` 부여 | 그 폴더 한 칸에만. 폴더는 보이는데 안은 안 보인다 |
| `expires_at` 경과 | 무효. 시간이 유일하게 자동으로 좁혀지는 축이다 |
| 위키 유래 부여 | 항상 파일 단위·비상속 → 같은 폴더의 PDF·이미지는 안 열린다 |

폴더가 보이는 것과 그 안이 보이는 것은 다르다. 폴더 ZIP 다운로드는
`can_access_descendants` 로 별도 판정한다.

### 이동

항목을 옮기면 상속 경로가 통째로 갈린다. 원래 권한이 따라가지 않는다 — `@전사` 상속 폴더에
넣는 순간 전사 공개가 되고, 빼면 사라진다. `invalidate_path_stakeholders` 가 **옮기기 전후 두
경로**의 이해관계자(경로상 폴더 소유자 + 그 폴더에 권한이 부여된 그룹의 멤버) 캐시를 턴다.
위키 상태도 `wiki.sync_file` 이 상속을 재판정한다.

### 두 축이 만나는 지점

| 상황 | 결과 |
|---|---|
| 폴더 위키 ON → 하위 파일 소유자가 그 파일만 끄기 | 동작한다 (명시 FALSE + 직접 부여 회수) — 소유자 탈출구 |
| 권한 화면에서 `@전사` 회수 | 위키도 함께 꺼진다 (`disable_for_public_revoke`) |
| 권한 화면에서 폴더에 `@전사 read` + 하위 상속 | 위키 탈출구가 통하지 않는다 — 아래 참조 |

#### 폴더에 `@전사` 상속 부여를 막지 않는다 (2026-07-30 결정)

폴더에 `@전사 read` 를 상속 부여하면 하위 파일 소유자가 위키를 꺼도 상속된 공개가 남는다.
위키 토글이 폴더 상속 부여를 피하는 이유가 바로 이건데, 권한 화면에는 같은 가드가 없다.

**가드를 넣지 않기로 했다.** 권한 화면의 부여는 위키 토글의 지름길이 아니라 사람이 명시적으로
"이 폴더를 이렇게 공유한다"고 말한 것이고, 상속은 상속대로 동작해야 한다. `@전사` 만 특별히
상속에서 빼면 다른 그룹과 다르게 동작하는 두 번째 종류의 그룹이 생긴다 — 이 설계가 계속
피해 온 구조다. 그 폴더의 공개가 싫은 파일은 **다른 폴더로 옮긴다.** 위치가 곧 권한이다.

## 그 밖의 규칙

- 접근 불가는 **404**(존재 은닉), 읽기는 되는데 manage 부족이면 **403**.
- `manage` 권한자는 타인 파일도 발행/부여할 수 있다. 폴더 발행은 파일마다 `manage` 를
  재판정한다 — 틀리더라도 발행 누락 방향이라 안전하다(spec/wiki-index.md 「폴더 발행 범위」).
- `shared-with-me` 는 `is_system` 그룹(`@전사`) 유래 부여를 숨긴다. **UI 필터지 보안 필터가
  아니다** — 권한은 실제로 있고 파일도 열린다. 위키 문서를 찾는 자리는 문서 카탈로그다.
- 시스템 admin(`users.role`)은 파일 내용 접근 권한이 없다 (PRD 3.6.4).
- 공유 링크(`SharePermission` read/download/write)는 **비로그인 방문자 전용의 별개 축**이다.
  그룹 권한 모델과 섞이지 않는다.
- 판정 결과는 사용자별 세대 카운터(`perm:ugen:{user_id}`)로 캐시하고, 부여/회수/그룹 멤버
  변경 시 세대를 올려 일괄 무효화한다. 정확성이 적중률보다 우선이라 redis 오류 시 항상 DB 판정.
