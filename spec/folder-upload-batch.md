# 폴더 업로드 — 배치 다중 파일 업로드

작성: 2026-07-21. 사용자 결정: 클라이언트 zip 압축 + 서버 압축 해제 방식 대신,
한 요청에 여러 파일 + 상대 경로를 실어 보내는 배치 방식을 채택.

현재 폴더 업로드는 불가능하다. `<input type="file">` 에 `webkitdirectory` 가 없고
(`FileBrowserPage.tsx:707`), 드롭 핸들러는 `dataTransfer.files` 만 읽으며
(`FileBrowserPage.tsx:570`), `runUpload()` 는 평평한 `File[]` 을 전부 현재
`parentId` 한 곳에 올린다(`FileBrowserPage.tsx:408`). `webkitRelativePath` 를
읽는 코드는 저장소 전체에 없다.

## 두 가지 업로드 경로

이 설계가 추가하는 경계는 **64MB 하나**뿐이다.

### 1. 단일 파일 업로드 — 기존, 변경 없음

| 크기 | 경로 |
|---|---|
| `≤ 1GB` | `POST /api/files/upload` (`routes/files.py:163`) |
| `> 1GB` | 재개 가능 업로드 — init → parts → complete (`routes/files.py:206~`) |

1GB 경계(`RESUMABLE_THRESHOLD`, `lib/resumable.ts:29`)는 이미 있는 동작이다.
폴더 업로드는 이 경로를 **그대로 재사용**한다 — `parent_id` 만 올바른 하위 폴더로
넘겨주면 된다. 청킹·일시정지·재개·세션 복구가 전부 따라온다.

### 2. 배치 업로드 — 신규

`64MB 이하` 파일만 모아 한 요청으로 보낸다.

배치가 푸는 문제는 **요청 수**다. `rate_limit_upload_per_min = 10`(user 당,
`core/config.py:59`)이라 파일 하나씩 올리면 500개 폴더가 50분이다.
배치당 200개면 분당 2000파일이고, **rate limit 설정값은 건드리지 않는다.**

64MB 를 넘는 파일은 배치에 담지 않는다. 파일 하나가 이미 요청 하나 값을 하므로
묶을 이득이 없고, 큰 파일이 배치를 인질로 잡으면 실패 시 재전송 비용만 커진다.
그런 파일은 위의 단일 경로로 보낸다.

### 왜 zip 이 아닌가

배치는 각 경로 세그먼트가 `create_folder` 의 `name` 이 되어 **DB 행만** 만들고,
오브젝트 키는 `build_file_key(user_id, file_id)`(`services/files.py:56`)로
**id 기반**이라 사용자가 준 경로 문자열이 스토리지 키에 전혀 들어가지 않는다.
경로 탈출이 구조적으로 불가능하다.

zip 해제는 zip bomb·엔트리 경로 탈출·심볼릭 링크를 직접 방어해야 하고,
해제 전에는 실제 크기를 몰라 `_reserve_quota`(`services/files.py:309`)의
선점 모델과 맞지 않는다. 이 스택엔 워커/큐도 없어 해제가 앱 워커를 물고 늘어진다.

## 백엔드

### 설계의 핵심 — 기존 `upload_file` 재사용

`files_service.upload_file` 은 **파일마다 독립적으로 commit** 한다
(`services/files.py:493`). 실패 시 `rollback()` 은 이미 커밋된 앞선 파일에
영향을 주지 않는다. 따라서 배치 서비스는 `upload_file` 을 감싸는 얇은 루프로
충분하다 — 할당량 선점, MinIO 스트리밍, `file_versions` v1 기록, 썸네일 생성,
SSE 이벤트 발행이 전부 무료로 따라온다.

새로 쓰는 코드는 **경로 → 폴더 id 해석**과 **부분 성공 응답** 두 가지뿐이다.

부분 성공은 예외가 아니라 정상 경로다. 200개 중 3개가 409(동명 충돌)로
실패해도 나머지 197개는 올라가야 한다.

### rollback 이 남기는 함정 (구현 중 발견)

`upload_file` 과 `create_folder` 는 실패 시 `session.rollback()` 을 호출하는데, 그러면
세션에 붙은 ORM 인스턴스가 **전부** expire 된다 — 요청 스코프의 `user` 를 포함해서.
배치는 실패 후에도 다음 항목을 계속 처리하므로, 다음 반복에서
`ensure_file_access` 가 `user.id` 를 읽는 순간(`services/files.py:82`) 비동기 컨텍스트
밖 lazy load 가 일어나 `MissingGreenlet` 으로 죽는다.

요청당 파일이 하나인 단일 업로드에서는 rollback 직후 요청이 끝나 드러나지 않던 문제다.
"부분 실패 후 계속 진행"이라는 배치의 성질이 처음으로 드러낸다. 대응 둘:

- `_revive_user` 로 expire 된 `user` 를 명시적으로 다시 읽는다. 각 항목/세그먼트 처리
  직전에 호출한다.
- 폴더 id 는 ORM 인스턴스가 아니라 **int 로만** 들고 다닌다(`_ensure_folder_path` 가
  `list[int]` 를 반환하는 이유).
- 성공한 File 은 `session.expunge` 로 세션에서 떼어낸다. 뒤 항목이 실패해 rollback 이
  돌아도 응답 직렬화 시점에 expire 되어 있지 않게 한다.

배치 루프에서 ORM 객체를 세션에 걸친 채 재사용하는 코드를 추가할 때는 이 제약을
다시 확인해야 한다.

### `POST /api/files/batch`

`multipart/form-data`,
`dependencies=[Depends(rate_limit_user("upload", "rate_limit_upload_per_min"))]`
— 기존 `/upload` 와 같은 scope.

| 필드 | 타입 | 설명 |
|---|---|---|
| `files` | `UploadFile[]` | 반복 필드. 0개 가능(폴더만 만드는 요청) |
| `paths` | `str[]` | `files` 와 같은 순서·개수. 파일명 포함 상대 경로 (`"docs/img/a.png"`) |
| `dirs` | `str[]` | 선택. 미리 만들어 둘 디렉터리 경로 |
| `parent_id` | `Form(int \| None)` | 배치가 놓일 기준 폴더. 생략 시 루트 |

`len(files) != len(paths)` 면 422.

### 응답 (200)

```json
{
  "items": [
    {"path": "docs/a.png", "status": "created", "file": { /* FileResponse */ }},
    {"path": "docs/b.png", "status": "error", "code": 409,
     "detail": "같은 이름의 파일이 이미 있습니다."}
  ],
  "folders": {"docs": 42, "docs/img": 43},
  "succeeded": 1,
  "failed": 1
}
```

전부 실패해도 200이다. HTTP 상태는 "배치 요청이 처리됐는가"를 뜻하고,
개별 결과는 `items` 가 말한다. 프론트가 재시도 대상을 골라내려면 항목별
`code` 가 필요하다.

`folders` 는 개수가 아니라 **경로 → 폴더 id 맵**이며, 이번에 만든 것과 기존 것을
가리지 않고 이 요청이 해석한 전 경로를 담는다. 64MB 초과 파일을 단일 경로로 보낼 때
`parent_id` 를 여기서 꺼낸다.

### 경로 정규화 (`_normalize_relpath`)

이 함수가 유일한 신뢰 경계다. 순서대로:

1. `\` → `/` 치환 (Windows 클라이언트)
2. `/` 로 분리, 빈 세그먼트와 `.` 제거
3. `..` 가 **하나라도** 있으면 422 — 상쇄 계산 없이 즉시 거부
4. 절대 경로(`/` 시작), 드라이브 문자(`C:`) 거부
5. 세그먼트별: NUL·제어문자(`\x00-\x1f`) 거부, `strip()` 후 빈 문자열 거부,
   길이 255 초과 거부
6. 깊이 32 초과, 전체 경로 길이 4096 초과 거부
7. 마지막 세그먼트 = 파일명, 앞쪽 = 디렉터리 경로

`create_folder`(`services/files.py:340`)가 이미 `name.strip()` 후 빈 값이면 422를
던지지만, 배치는 폴더를 만들기 **전에** 전 경로를 검증해야 절반만 만들어진 트리를 피한다.

### 폴더 해석 (`_ensure_folder_path`)

요청 스코프의 `dict[tuple[int, str], int]` 캐시(부모 id + 이름 → 폴더 id)를 두고
세그먼트마다:

1. 캐시 히트 → 재사용
2. 미스 → `parent_folder_id`, `name`, `is_deleted = False` 로 조회
   - 폴더가 있으면 재사용 (**기존 폴더에 병합**)
   - 같은 이름의 *파일*이 있으면 이 경로의 모든 항목을 409로 실패 처리
3. 없으면 `create_folder` 호출.
   409(`IntegrityError`)가 오면 **재조회해서 재사용** — 두 배치가 동시에 같은
   폴더를 만들려 할 때 `uq_files_sibling_name` 부분 유니크 인덱스
   (`models/file.py:99`, `is_deleted = FALSE` 조건부)가 하나를 떨군다.
   이 재조회가 없으면 동시 업로드가 산발적으로 깨진다.

권한은 최상위 `parent_id` 에서 `_resolve_parent(need="write")` 로 **한 번만**
검증한다(`services/files.py:255`). 그 아래 폴더는 전부 우리가 부모 id 를 지정해
만들거나 부모 id 로 조회한 것이므로 구조적으로 후손이 보장된다.

### 상한

`core/config.py` 에 추가:

```python
max_batch_files: int = 200                 # 배치당 파일 수
max_batch_bytes: int = 64 * 1024 * 1024    # 배치 합계 (파일당 상한이 아니다)
```

`max_batch_bytes` 는 요청 본문 전체의 합계다. 파일 1개 상한은 기존
`MAX_FILE_SIZE = 10GB`(`services/files.py:41`) 그대로이고 배치는 이를 바꾸지 않는다.

`Content-Length` 로 **파싱 전에** 차단한다. Starlette 의 multipart 파서는 이미
전부 읽은 뒤에야 핸들러에 넘기므로, 본문을 다 받고 거부하면 상한의 의미가 없다.

nginx 는 전역 `client_max_body_size 10g`(`nginx/conf.d/default.conf:9`)이므로
`/api/files/batch` 만 별도 `location` 으로 분리해 `client_max_body_size 80m` 을
건다. 게이트웨이에서 먼저 떨어뜨리는 게 백엔드 워커를 지키는 길이다.

### 메모리

Starlette 은 파일당 `SpooledTemporaryFile`(1MB 초과 시 디스크 스풀)을 쓰고,
`_upload_size`(`services/files.py:410`)는 `.size` 를 먼저 읽어 전체 적재를 피한다.
64MB 상한이면 워커당 최악 64MB 디스크 스풀이다. 배치 내 파일은 **순차 처리**한다 —
DB 세션이 하나라 어차피 직렬이고, 동시 처리는 MinIO 커넥션 경합만 늘린다.

## 프론트

### 트리 수집 (`lib/fileTree.ts`)

두 입구가 서로 다른 API 를 쓴다. 산출물은 양쪽 다
`{ files: {path, file}[], dirs: string[] }`.

**폴더 선택 버튼** — `webkitdirectory` 를 **새 input + 새 ref** 로 추가한다.
기존 `fileInputRef`(`FileBrowserPage.tsx:707`)에 붙이면 개별 파일 선택이
불가능해지므로 반드시 분리한다. `file.webkitRelativePath` 가
`"선택폴더/docs/a.png"` 형태로 이미 상대 경로다.

**드래그 앤 드롭** — `dataTransfer.items` → `webkitGetAsEntry()` 재귀. 함정 둘:

- `dataTransfer` 는 이벤트 핸들러가 반환되면 무효화된다. `await` 전에
  `items` 를 **동기적으로** 배열로 복사해야 한다.
- `FileSystemDirectoryReader.readEntries()` 는 한 번에 최대 100개만 준다.
  **빈 배열이 올 때까지 반복 호출**해야 한다. 한 번만 부르면 101번째부터
  조용히 사라진다.

### 오케스트레이션 (`lib/folderUpload.ts`)

**1단계 — 트리 확정.** 전 디렉터리 경로를 `dirs` 로만 채운 요청(파일 0개)을 먼저
보내고 `folders` 맵을 받는다. 이걸로 배치·단일 양쪽이 같은 `parent_id` 를 공유한다.
1.5GB 파일 하나만 든 폴더처럼 배치에 파일이 하나도 없는 폴더도 여기서 id 를 얻는다.

**2단계 — 파일 전송.** 크기로 나눠 보낸다.

- `≤ 64MB` → greedy 하게 묶어 배치. 파일 수 ≤ 200, 합계 ≤ 64MB.
  배치 **2개씩 동시 실행**. 그 이상은 서버 DB 세션 경합만 늘린다.
- `> 64MB` → `folders` 맵에서 `parent_id` 를 꺼내 기존 함수를 그대로 호출.
  `uploadFile()` 또는 `startNewResumableUpload()` — 1GB 분기는 그쪽이 알아서 한다.

폴더가 깊으면 상위 폴더가 여러 배치에서 반복 요청되지만, `_ensure_folder_path` 가
기존 폴더를 재사용하므로 안전하다.

### 진행률 UI

배치의 `onUploadProgress` 를 파일별로 쪼개면 부정확하다. 폴더 업로드는
**태스크 하나로 집계**한다 — 기존 `uploads` state(`{id, name, percent, status}`)에
`name: "폴더명 (N/M)"`, `percent = 완료 바이트 / 전체 바이트`.
개별 실패는 완료 후 요약 토스트로: "3개 실패 — 자세히 보기".

## 제약 표시와 에러 메시지

### 보여줄 제약과 숨길 제약

| 제약 | 값 | 사용자에게 |
|---|---|---|
| 파일 1개 최대 크기 | 10GB (`services/files.py:41`) | **보임** |
| 남은 저장 용량 | `max_storage - storage_used` (`schemas/auth.py:73`) | **보임** |
| 폴더 깊이 | 32단계 | 위반 시에만 |
| 이름 길이 | 255자 | 위반 시에만 |
| 이름 금지 문자 | 제어문자, `/`, `\` | 위반 시에만 |
| 배치 파일 수 / 합계 | 200개 / 64MB | **숨김** |
| rate limit | 10회/분 | **숨김** |

아래 둘은 **절대 노출하지 않는다.** 클라이언트가 알아서 분할하고 배치가 흡수하는
전송 계층의 내부 사정이지, 사용자가 지켜야 할 규칙이 아니다. "한 번에 200개까지"
같은 안내는 실제로는 존재하지 않는 제약을 있는 것처럼 만든다.

평상시 노출은 업로드 영역에 한 줄이면 충분하다:
`파일 1개 최대 10GB · 남은 용량 8.4GB`

### 사전 검사 (업로드 시작 전)

**바이트 하나 보내기 전에** 클라이언트가 전 항목을 검증한다. 2GB 를 올린 뒤
쿼터 초과로 실패하는 건 최악의 UX다. 트리 수집 직후, 1단계 요청 전에 돌린다.

검사 항목은 `_normalize_relpath` 와 **같은 규칙**을 쓴다(`lib/fileTree.ts` 에
공유 함수로 두고 양쪽이 호출). 규칙이 갈라지면 클라가 통과시킨 걸 서버가
거부하는 상황이 생긴다.

확인 다이얼로그:

```
"사진" 폴더 업로드
─────────────────────────────────────
파일 342개 · 폴더 12개 · 총 2.1GB
남은 용량 8.4GB → 업로드 후 6.3GB

⚠ 3개를 건너뜁니다
  movie.mkv — 12.0GB (파일 1개 최대 10GB)
  a/b/…/deep.txt — 폴더 깊이가 32단계를 넘습니다
  report<제어문자>.txt — 이름에 쓸 수 없는 문자가 있습니다
─────────────────────────────────────
              [취소]  [342개 업로드]
```

위반 항목이 없으면 경고 블록 없이 요약만 띄운다. 건너뛸 항목이 있어도
**나머지는 그대로 진행**한다 — 파일 하나 때문에 폴더 전체를 막지 않는다.

사전 검사 메시지:

| 조건 | 메시지 |
|---|---|
| 10GB 초과 | `{이름} — {크기} (파일 1개 최대 10GB)` |
| 깊이 32 초과 | `{경로} — 폴더 깊이가 32단계를 넘습니다` |
| 이름 255자 초과 | `{이름} — 이름이 255자를 넘습니다` |
| 제어문자·`..` | `{이름} — 이름에 쓸 수 없는 문자가 있습니다` |
| 이름이 공백뿐 | `{경로} — 이름이 비어 있습니다` |
| 합계 > 남은 용량 | `총 {합계}를 올리기에 남은 용량이 부족합니다 (남은 용량 {잔여}). {부족분}을 확보하거나 일부만 선택해 주세요.` — 이 경우만 업로드 버튼 비활성화 |
| 전부 걸러짐 | `업로드할 수 있는 파일이 없습니다.` |

쿼터 사전 검사는 **UX 일 뿐 강제가 아니다.** 검사와 실제 업로드 사이에 다른
세션이 용량을 쓸 수 있고, 최종 판정은 `_reserve_quota` 의 조건부 UPDATE
(`services/files.py:309`)가 한다. 사전 검사를 통과해도 413 이 올 수 있으므로
아래 서버 에러 처리가 여전히 필요하다.

### 서버 에러 → 메시지

배치 응답 `items[].code` 와 단일 경로의 HTTP 상태를 **같은 함수**로 문자열에
매핑한다. `FileBrowserPage.tsx:441-448` 에 이미 같은 매핑이 인라인으로 있으므로,
`lib/uploadError.ts` 로 추출해 배치·단일·재개 세 경로가 공유한다.

| 코드 | 메시지 |
|---|---|
| 409 | `같은 이름의 항목이 이미 있습니다` |
| 413 (용량) | `저장 용량을 초과했습니다` |
| 413 (크기) | `파일 크기 상한(10GB)을 초과했습니다` |
| 403 / 404 | `이 폴더에 업로드할 권한이 없습니다` |
| 422 | `경로나 이름에 쓸 수 없는 문자가 있습니다` |
| 502 | `저장소 오류로 저장하지 못했습니다` |
| 그 외 | `업로드에 실패했습니다` |

**429 는 사용자에게 보이지 않는다.** `Retry-After` 헤더(`api/deps.py:105`)만큼
기다렸다 자동 재시도하고, 진행률 태스크 상태만 "대기 중"으로 바꾼다. 배치가
rate limit 을 흡수하는 게 이 설계의 목적이므로 사용자가 429 를 본다면 그건
설계가 실패한 것이지 사용자가 고칠 수 있는 문제가 아니다.

### 결과 표시

**파일마다 토스트를 띄우지 않는다.** 폴더 업로드는 수백 개라 개별 토스트는
화면을 덮는다. 기존 `notifyUploadSuccess`(`FileBrowserPage.tsx:385`)가
파일당 토스트를 띄우므로, 폴더 업로드 경로에서는 이를 우회한다.

- 전부 성공 → `toast.success("342개 파일을 업로드했습니다.")`
- 부분 실패 → `toast.error("339개 완료 · 3개 실패")` + 진행률 태스크에
  [자세히] 버튼. 누르면 실패 목록 모달(경로 + 사유), **[실패한 항목만 재시도]** 제공
- 전부 실패 → `toast.error("업로드에 실패했습니다. 자세히 보기")`

재시도는 실패 목록을 그대로 새 업로드 작업으로 돌린다. 폴더는 이미 만들어져
있고 `_ensure_folder_path` 가 기존 폴더를 재사용하므로 그대로 다시 태우면 된다.

### SSE 이벤트 폭주

`upload_file` 은 파일마다 `publish_file_event` 를 호출한다(`services/files.py:502`).
200개 배치면 200개 이벤트가 같은 폴더를 보는 모든 사용자에게 간다. Phase 8-1 의
300ms 디바운스(`spec/drive-ux-phase8.md`)가 목록 재조회를 병합하므로 화면은
버티지만, 업로드 주체 본인은 전체가 **끝난 뒤 한 번** `afterUpload()` 하도록 막아둔다.
서버 측 집계 이벤트는 v2 과제.

## 명시적으로 하지 않는 것

- **zip 업로드 후 서버 해제** — 사용자가 이미 갖고 있는 zip 을 펼치는 건 그 자체로
  유효한 별도 기능이다. 워커 분리·압축률 상한·엔트리 수 제한을 갖춰 따로 설계한다.
- **단일 업로드 경로 수정** — 폴더 업로드는 `parent_id` 만 다르게 넘길 뿐
  기존 경로를 손대지 않는다.
- **서버 측 배치 집계 SSE 이벤트** — 디바운스로 v1 은 버틴다.
- **배치 단위 원자성** — 부분 성공이 의도된 동작이다. 전부-또는-전무를 원하면
  이미 커밋·저장된 파일을 되감아야 하는데, 그 비용이 재시도 UI 보다 크다.

## 미결

- `max_batch_bytes` 64MB 는 회선 안정성에 따른 절충값이다. 안정적인 사내망이면
  128MB 로 올려 요청 수를 더 줄이고, 불안정하면 32MB 로 낮춰 재전송 비용을 줄인다.
- 64MB 초과 파일은 각자 요청 하나를 쓰므로 분당 10개 제한에 걸린다. 이 구간 파일
  10개면 이미 640MB+ 전송이라 대기보다 전송이 지배적이지만, 실제로 문제가 되면
  `rate_limit_upload_per_min` 을 올린다.
