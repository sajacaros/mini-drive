# 그룹 게시판 — 관리자가 만들고 그룹으로 여는 글판

작성: 2026-08-05. 사용자 결정:

- 게시판은 **시스템 관리자(`admin`/`super_admin`)만** 만들고, 이름을 고치고, 지운다. 게시판별
  운영자 역할은 두지 않는다.
- 게시판에 **그룹을 할당**해서 연다. 게시판↔그룹은 **N:M** 이고, 할당마다 `read`/`write` 가
  갈린다.
- **권한축을 새로 판다.** 드라이브의 `file_group_permissions` 를 재사용하지 않는다(아래).
- 첨부는 드라이브 `files` 와 **분리**한다. 개인 할당량을 차감하지 않고, 작다.
- 글을 지우면 첨부 오브젝트를 **그 자리에서 회수**한다. 유예도 사이드카도 없다.
- 권한을 잃으면 **글은 남고 접근만 끊긴다.** 작성자 본인도 예외가 아니다.
- 댓글은 넣는다. 가시성은 글과 **같은 게이트 하나**를 탄다.

큰 파일은 드라이브에 올리고 공유 링크를 글에 붙인다. 게시판 첨부가 작아도 되는 이유가 이것이다 —
드라이브가 이미 있는데 그 옆에 두 번째 파일 저장소를 세울 이유가 없다.

---

## 왜 드라이브 권한축을 쓰지 않는가

게시판을 `files` 트리의 폴더로 만들면 권한·업로드·미리보기가 전부 공짜로 딸려온다. 그래도
분리하는 이유가 셋이다.

**첫째, 상속 방향이 게시판에 해롭다.** `spec/permissions.md` 의 규칙은 *상속은 넓히기만 한다,
하위에서 못 좁힌다* 이다. 게시판 폴더에 `@전사 read` 가 한 번 붙으면 그 아래 글은 되돌릴 방법이
없고, 좁히는 유일한 수단인 `inherit_to_children=FALSE` 는 게시판에 아무 의미가 없다 — 게시판은
트리가 아니라 평평하기 때문이다. 넓히기 전용 비대칭은 폴더 계층에서 값을 하는 성질이지, 칸 하나
짜리 구조에서는 잃는 것만 남는다.

**둘째, 글은 파일이 아니다.** 글은 제목·본문·작성자·댓글을 가진 레코드다. 이걸 `files` 행으로
만들면 버전·휴지통·위키 토글·썸네일·ZIP·`baseVersion` 충돌 감지가 전부 따라붙는데 게시판에서는
하나도 쓰이지 않는다. 쓰이지 않는 경로는 검증되지 않고, 유출은 검증되지 않은 두 번째 경로에서
난다(`spec/wiki-index.md` 「왜 별도의 위키 접근 경로가 아닌가」와 같은 논지, 방향만 반대다).

**셋째, 판정이 조인 한 번이다.** 드라이브는 조상 경로를 recursive CTE 로 훑고 세대 카운터로
캐시한다. 게시판은 상속이 없으니 `내 그룹 ∩ 이 게시판에 할당된 그룹` 한 번이면 끝난다. CTE 도
Redis 캐시 무효화도 필요 없다.

대가도 적어 둔다. 첨부의 미리보기·썸네일·ZIP 다운로드를 못 얻는다. 1차는 **다운로드만** 한다.

## 데이터 모델

| 테이블 | 내용 |
|---|---|
| `boards` | `id`, `name`(활성 UNIQUE), `description`, `created_by`, `is_active`, `created_at`, `updated_at` |
| `board_groups` | `board_id`, `group_id`, `permission`(`read`\|`write`), `granted_by`, `granted_at`. UNIQUE(board_id, group_id) |
| `board_posts` | `id`, `board_id`, `author_id`, `title`, `body`(마크다운), `is_deleted`, `deleted_at`, `created_at`, `updated_at` |
| `board_comments` | `id`, `post_id`, `author_id`, `body`, `is_deleted`, `deleted_at`, `created_at` |
| `board_attachments` | `id`, `post_id`, `object_key`, `filename`, `mime_type`, `size`, `uploaded_at` |

삭제는 전부 소프트 삭제다. 게시판은 `is_active=FALSE`, 이름 점유도 활성 게시판으로만 한정한다 —
`groups` 가 `uq_groups_name_active` 로 푼 것과 같은 문제이고 같은 해법을 쓴다.

`BoardPermission` 은 `read`/`write` **두 단계**의 새 `StrEnum` 이다. 드라이브의
`GroupPermission`(read/write/manage)을 재사용하지 않는다 — `manage` 가 게시판에는 없는 개념인데
값만 받아들이면 언젠가 저장되고, 그때 두 축이 의미 없이 얽힌다.

`@전사` 시스템 그룹이 이미 있으므로 전사 공지판은 별도 기능 없이 나온다: `@전사 read` +
운영팀 `write`.

## 단일 관문

`ensure_board_access(session, user, board_id, need)` 하나로 모은다. 드라이브의
`ensure_file_access` 대응이고, 게시판·글·댓글·첨부의 **모든** 경로가 이것을 먼저 탄다.

> **유효 권한 = 내가 속한 그룹 중 이 게시판에 할당된 것들의 최고 수준.** (write > read)

`get_user_group_ids`(`services/groups.py`)를 그대로 쓴다. 시스템 그룹은 멤버십을 물질화하지 않고
그 함수가 활성 사용자에게 항상 끼워 넣으므로, `@전사` 할당도 자동으로 맞는다.

- 접근 불가는 **404**(존재 은닉). 읽기는 되는데 쓰기가 없으면 **403**. 드라이브와 같은 규약이다.
- 게시판 목록은 **내가 접근 가능한 것만** 돌려준다. 이름조차 나오지 않는다.

## 권한을 잃으면

| 상황 | 결과 |
|---|---|
| 그룹에서 빠짐 / 그룹 할당이 회수됨 | 그 게시판의 글·댓글·첨부 전부 404 |
| **내가 쓴 글**인데 접근을 잃음 | 마찬가지로 404. 수정·삭제도 못 한다 |
| 계정이 `inactive` 가 됨 | 접근 끊김. 글·댓글은 남고 작성자 이름도 그대로 표시된다 |
| 글이 삭제됨 | 그 글의 댓글·첨부도 함께 잠긴다. 목록·상세 어디에도 안 나온다 |
| 권한을 다시 얻음 | 남아 있던 글이 그대로 다시 보인다 |

작성자 본인에게 예외를 두지 않는 이유는 규칙을 하나로 유지하기 위해서다. *게시판 접근이 곧 글
접근* 한 줄이면 목록·상세·댓글·첨부 다운로드·수정·삭제가 전부 같은 판정을 쓴다. 예외를 하나
두는 순간 여섯 자리에서 각각 "본인인가?"를 다시 묻게 되고, 그 중 하나를 빠뜨리면 그게 구멍이다.

## 첨부

- 파일당 **10 MB**, 글당 **5개**. `board_attachment_max_bytes` / `board_attachment_max_count`
  로 `Settings` 에 둔다.
- **개인 할당량을 차감하지 않는다.** 드라이브 사용량 통계에도 잡히지 않는다.
- MinIO 는 같은 버킷, 키만 `board/{board_id}/{post_id}/{uuid}` 로 가른다.
- 업로드는 단일 요청 `multipart/form-data`. 10 MB 상한이라 재개 가능 업로드·멀티파트가 필요 없다.
- 다운로드만 지원한다. 미리보기·썸네일 없음.

### 회수는 삭제하는 그 자리에서 한다

글을 지우면 **그 요청 안에서** `board_attachments` 행을 지우고 MinIO 오브젝트를 회수한다.
사이드카도 유예 기간도 없다.

순서는 `purge_tree`(`services/files.py:1559`)의 규약을 그대로 쓴다.

1. 지울 `object_key` 를 모은다.
2. DB 확정 — 첨부 행 삭제(하드), 글은 `is_deleted=TRUE`. 커밋.
3. `storage.delete_many_async(keys)` — **best-effort**. 실패해도 DB 는 이미 일관하다.

드라이브가 첨부를 7일 붙들고 있는 이유는 휴지통에서 되살릴 수 있어서다. 게시판 글에는 **복원
경로가 없으므로** 붙들 이유가 없다. 게시판용 정리 루프를 새로 만드는 것은 보이지도 않는 유예를
위해 스케줄러 코드를 하나 더 두는 셈이다.

개인 할당량을 차감하지 않는 것이 여기서 한 번 더 값을 한다. `purger` 가 Redis 리스를 쓰는 이유는
같은 항목을 두 프로세스가 집으면 `_release_quota` 가 이중 차감되기 때문인데(spec/trash-retention-purge.md),
게시판에는 되돌릴 사용량 자체가 없다. 두 번 지워도 두 번째가 무해하다.

같은 경로를 세 곳이 공유한다 — 글 삭제, 글 수정 중 첨부 개별 제거, 게시판 삭제. 게시판 삭제는
글이 많을 수 있으므로 키 수집을 한 쿼리로 하고 `delete_many` 를 1000개씩 끊어 호출한다.

**대가**: 실수로 지운 글의 첨부는 되살릴 수 없다. 본문·댓글은 행이 남아 관리자가 DB 에서 복구할
여지가 있지만 오브젝트는 그 순간 사라진다. 첨부가 파일당 10 MB 로 작고 원본이 대개 올린 사람
로컬이나 드라이브에 있다는 전제에서 받아들인다.

**남는 구멍 하나**: 3단계가 실패하면 오브젝트가 고아로 남고 아무도 다시 시도하지 않는다.
드라이브도 같은 자리에서 같은 선택을 했다(`purge_tree` 4단계). DB 를 진실 소스로 두는 대가이고,
회수하려면 키를 아는 쪽이 DB 인데 그 행이 이미 없다.

## 댓글

가시성은 글과 같은 게이트라 따로 정할 게 없다. 나머지는 이렇게 잡는다.

- 댓글 작성에는 `write` 가 필요하다. `read` 만 있으면 읽기만 된다.
- **수정은 없다.** 지우고 다시 쓴다.
- 삭제는 작성자 본인과 시스템 관리자. 소프트 삭제이고 자리는 "삭제된 댓글입니다"로 남긴다 —
  아래 답글이 대화 맥락을 잃지 않게.
- 대댓글은 없다. 평평한 목록 하나다.
- 첨부는 글에만 붙는다. 댓글에는 없다.
- 글 목록에 댓글 수를 같이 준다.

## admin 이 게시판 내용을 보는가 — 새로 정한 것

드라이브 원칙은 *admin 도 파일 내용에는 접근할 수 없다*(PRD 3.6.4)이다. 게시판에는 그대로
옮기지 **않는다.**

그 원칙의 근거는 개인 드라이브의 사생활이다. 게시판은 관리자가 만들고 관리자가 그룹을 붙인
**조직의 공용 공간**이라 성격이 다르다. 그리고 글·댓글 삭제 권한을 관리자에게 준 이상, 못 읽는
글을 지우게 하는 것은 성립하지 않는다.

> 시스템 관리자는 모든 게시판을 **읽고**, 글·댓글을 **삭제**할 수 있다. 다만 **쓰지는 못한다** —
> 글·댓글 작성은 해당 그룹의 `write` 가 있어야 한다.

관리자의 열람은 감사 로그에 남기지 않는다(목록 조회마다 행이 쌓인다). 삭제와 게시판 관리는
남긴다: `board.create`, `board.update`, `board.delete`, `board.group_grant`,
`board.group_revoke`, `board.post_delete`, `board.comment_delete`.

## API

| 메서드 | 경로 | 권한 |
|---|---|---|
| GET | `/api/boards` | 접근 가능한 게시판 목록 (내 유효 권한 포함) |
| POST/PATCH/DELETE | `/api/admin/boards[/{id}]` | 관리자 — 생성·수정·삭제 |
| GET/POST/DELETE | `/api/admin/boards/{id}/groups[/{group_id}]` | 관리자 — 그룹 할당·회수 |
| GET | `/api/boards/{id}/posts` | `read` — 페이지네이션, 최신순 |
| POST | `/api/boards/{id}/posts` | `write` |
| GET/PATCH/DELETE | `/api/boards/{id}/posts/{post_id}` | `read` / 작성자 / 작성자·관리자 |
| GET/POST | `/api/boards/{id}/posts/{post_id}/comments` | `read` / `write` |
| DELETE | `/api/boards/{id}/posts/{post_id}/comments/{cid}` | 작성자·관리자 |
| POST/DELETE | `/api/boards/{id}/posts/{post_id}/attachments[/{aid}]` | `write` / 작성자·관리자 |
| GET | `/api/boards/{id}/posts/{post_id}/attachments/{aid}/download` | `read` |

글 수정은 작성자 본인만 한다. 관리자는 지울 수는 있어도 남의 글을 고치지는 못한다.

## 프런트

- 사이드바에 `게시판` 항목. 접근 가능한 게시판이 없으면 항목 자체를 감춘다.
- 본문은 마크다운. `components/Markdown.tsx` 가 이미 있어 새 의존성이 없다. 작성은 평문
  textarea + 미리보기 탭이면 충분하다.
- 게시판 관리(생성·그룹 할당)는 관리자 화면 안에 둔다. 그룹 선택 UI 는 `PermissionModal` 의
  그룹 선택을 재사용한다.

## 1차 범위 밖

게시판별 운영자 역할, 새 글 알림(SSE)·멘션, 위키 색인, 고정글(공지), 본문 검색, 글 수정 이력,
대댓글, 첨부 미리보기, 좋아요·조회수.

**위키 색인이 왜 빠지는가**는 짚어 둘 값이 있다. 게시판 글은 마크다운이라 색인 자체는 잘 맞지만,
위키의 *권한이 곧 검색 범위* 는 `file_group_permissions` 로 대상을 고르는 필터다. 게시판은 축이
다르므로 붙이려면 위키 쪽 대상 선정 단계를 두 축으로 고쳐야 한다. 게시판이 실제로 쌓인 뒤에
따로 다룬다.

## 남은 것

지금은 없다. 첨부 회수는 「회수는 삭제하는 그 자리에서 한다」로 닫혔다.
